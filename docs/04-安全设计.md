# 04-安全设计

> 生产级登录注册系统 · 安全设计（威胁模型、凭证、会话、防爆破、审计合规）
> 遵守 `设计规范.md` §1.7 认证授权与敏感数据、§2.4 敏感字段设计、§1.10 配置门禁；与 `01-架构设计.md`（D1–D9）、`02-API文档.md`（错误码/限流）、`03-数据库设计.md`（表结构）互为对照。

## 1. 威胁模型

| # | 威胁 | 攻击面 | 防护措施（对应章节） |
|---|---|---|---|
| T1 | 账号枚举 | 注册、登录、忘记密码、发码接口响应差异 | 统一文案（10101）、统一响应、防时序差异（§5.1） |
| T2 | 暴力破解 / 撞库 | 登录、2FA、验证码、重置密码 | 分层限流 + 账号锁定 423 + 验证码一次性（§4） |
| T3 | 会话固定 / 会话劫持 | 登录前后 Cookie | 登录后全量重签发、device_key 服务端生成、Refresh 轮换（§3） |
| T4 | 令牌重放 | Refresh 轮换、TOTP、验证码 | 轮换标记 + 重用检测、time-step 防重放、一次性消费（§3.4/§2.3） |
| T5 | CSRF | 状态变更接口 | Cookie SameSite=Strict + Path 隔离 + 双提交校验（§3.2） |
| T6 | XSS → 令牌窃取 | 前端渲染、富文本 | HttpOnly + 前端转义 + CSP（§3.2/§6） |

| T9 | 短信轰炸 | 发码接口 | 60s/次 + 10 次/日 + IP 频控 + 图形验证码预留（§4.3） |
| T10 | 数据泄露 | DB、日志、备份 | 敏感数据加密字段密文、PII 接口脱敏、审计留痕、日志脱敏（§2.4/§7） |

## 2. 凭证安全

### 2.1 密码（sc_users.password_hash）

- 算法：**bcrypt，cost=12**（规范化 §1.7 强制；兼容性如需升级到 argon2id，见 §8.3 轮换）
- 存储：`password_hash` 自包含盐与 cost，**不拆盐列**；`''` 空串表示未设置（仅 OAuth 建号用户）
- 校验：`password_verify`；服务端对「账号不存在」也执行一次假哈希，抹平时序差异（T1）
- 复杂度：8–72 位且含字母与数字（前端同规则校验，服务端为准）

### 2.2 一次性凭证（验证码 / 恢复码 / OAuth state / 重置凭证）

统一模式（规范 §1.7、03 §3.5）：

| 凭证 | 生成 | 存储 | 校验 | 失效 |
|---|---|---|---|---|
| 短信/邮件验证码 | `random_int(100000, 999999)` | `code_hash = sha256(salt + code)`，salt 独立列 | `hash_equals` | TTL 5 分钟、尝试 ≤5 次、消费即 `consumed_at`（条件更新，原子防并发重放） |
| 恢复码 | `random_bytes(8)` 转 hex，共 10 个 | 逐码 `sha256(salt+code)` | `hash_equals` | 一次性（`used_at` 条件更新）、随 2FA 关闭全部作废 |
| OAuth state | `random_bytes(32)` hex | 只存哈希，关联 user_id（绑定场景） | `hash_equals` + `consumed_at` 条件更新 | TTL 5 分钟 |
| 重置凭证 | 复用验证码通道 | 同验证码 | 同验证码 | 使用后全局吊销 token_version |

> 密文比较一律 `hash_equals`（防时序侧信道）；「尝试次数」在消费前用条件 UPDATE 原子递增（`attempts < max_attempts`），防并发绕过。

### 2.3 TOTP（Google Authenticator）

- Secret：32 字节 CSPRNG → Base32；**AES-256-GCM 加密后落库**（`totp_secret_encrypted`，加密密钥独立于 APP_KEY，见 §8.1）——TOTP 必须能解出明文计算 HMAC，故此处是唯一的「声称必须真实实现」的加密点
- 校验：±1 时间步容差；**同一 `(secret, time_step)` 防重放**（应用层在窗口内记录已用 time_step，或依赖短窗口 + 账号锁频兜底）
- 启用流程：`enable/start` 生成不落库 → 用户扫码 → `enable/verify` 校验通过才持久化（杜绝脏 secret 落库）
- 登录二次验证：票据 `totp_ticket` 为 5 分钟无状态签名票据（HMAC-SHA256，payload: uid/did），失败计入账号失败计数

### 2.4 OAuth 第三方 token

- 第三方 access/refresh token 仅在回调换取的当次使用；需要持久化的（如未做，预留）按 §2.3 同套 AES-256-GCM 加密存储（`sc_user_identities.access_token_encrypted`）
- 业务用不上的 token **不落库**，仅存 `(provider, provider_user_id)` 绑定关系

## 3. 认证会话安全

### 3.1 Cookie 属性矩阵（01 架构 D1 落地）

| Cookie | 值 | HttpOnly | Secure | SameSite | Path | Max-Age |
|---|---|---|---|---|---|---|
| `access_token` | JWT（无敏感信息） | ✅ | 生产 ✅ | Strict | `/api` | 15 分钟 |
| `refresh_token` | `random_bytes(32)`（仅哈希存库） | ✅ | 生产 ✅ | Strict | `/api/v1/auth/refresh` | 30 天 |
| `device_key` | `random_bytes(32)` 服务端生成（hex 存 CHAR(64)，03 §3.3） | ✅ | 生产 ✅ | Strict | `/` | 1 年 |

- **HttpOnly**：JS 无法读取 → XSS 无法窃取（T6）
- **SameSite=Strict**：跨站请求不携带 Cookie → 浏览器层 CSRF 主防线（T5）
- **Path 隔离**：Refresh 仅发送到刷新端点，缩减泄露面
- **Secure**：生产强制，Compose 开发环境（HTTP 内网）可关，需在 `.env` 显式声明
- **device_key 不信任任何客户端指纹**（D2）：值由服务端签发，无法伪造

### 3.2 CSRF 双保险

1. **浏览器层**：SameSite=Strict（同站 GET 之外的跨站请求不带 Cookie）
2. **应用层**：非幂等请求要求 `X-CSRF-Token` 头（值 = Access JWT 签名片段，服务端无状态校验；前端 axios 拦截器统一注入）。校验失败 → 419（code 10005）

> 因所有请求均携带自定义头（JSON 内容类型 + X-CSRF-Token），浏览器预检会拦下跨站表单 POST，此为纵深防御的第三层。

> **例外**：`POST /api/v1/auth/refresh` 豁免应用层 CSRF 校验——其凭证为 Refresh Cookie（HttpOnly + SameSite=Strict + Path=/api/v1/auth/refresh 隔离，跨站无法携带/读取，无 CSRF 风险面）；且该请求会携带 Access Cookie（Path=/api 匹配刷新路径），若强制校验头，会在 Access 与 csrf_token 同步过期时 419，破坏刷新链路（§3.4）。

### 3.3 登录会话生命周期

- 登录成功 → **全量重签发**（新 Access/Refresh/device_key，防会话固定 T3）
- 改密 / 重置密码 / 关闭 2FA / 全部下线 → `token_version+1`，**所有已签发 Access 与 Refresh 立即失效**
- 踢设备 → 吊销该设备全部 refresh token（D2）
- Access 无状态（payload: uid/ver/did），校验时比对 `ver == sc_users.token_version`——15 分钟窗口内被踢设备的 Access 仍可用（业务可容忍；若要求秒级失效，升级方案见 01 架构 §10 演进）

### 3.4 Refresh 轮换与重用检测（T4）

- 每次 `refresh`：旧 refresh 行标记 `rotated_at`（条件更新）→ 签发新 refresh（新行）→ 双 Cookie 重种
- 收到**已被轮换**的 token：
  - 同设备 / 同 IP（并发重试）→ 视为正常并发，返回新会话
  - 异设备 / 异 IP → **判定被盗用**：吊销该设备全部会话 + 审计 `refresh.reuse_detected` + 401（并建议告警邮件）
- 并发刷新原子性：事务内 `SELECT ... FOR UPDATE` 设备行（01 架构 D1）
- 每次 refresh 同时更新设备 `last_active_at` / `last_ip`

## 4. 防暴力破解矩阵（T2/T9）

### 4.1 分层限流（全部 429 + `X-RateLimit-*` 响应头）

| 层 | 维度 | 默认阈值 | 适用接口 | 存储 |
|---|---|---|---|---|
| L1 IP | 每分钟 | 注册 10 / 登录 20 / 其他登录态接口 20 | 全部 | Redis（降级 sc_rate_limits 表） |
| L2 账号 | 失败次数 | 密码登录/短信登录/重置：10 次 / 15 分钟 → 锁定 15 分钟（HTTP 423，响应头带剩余秒数）；2FA：5 次 / 15 分钟（§4.3） | 登录类接口 | sc_users 表原子 UPDATE |
| L3 验证码 | 尝试次数 | ≤5 次 / 码；60 秒重发间隔；10 次/日 | 发码、验码 | sc_verification_codes / Redis |
| L4 行为 | 图形验证码 | CaptchaProvider 预留，默认关闭（演示环境 mock） | 登录失败 ≥2 次后要求 | 无状态图签 |

- **账号锁定口径**：锁定状态仅对**确证存在的账号**以 423 表达；不存在的账号恒返回 10101（T1 防枚举 + 防撞库）
- **双锁定机制**（03 §3.1）：自动临时锁定记 `sc_users.locked_until`（失败 10 次锁 15 分钟，到点自动解除）；`sc_users.status=2` 为人工/风控长时锁定，两者独立判断、互不覆盖
- 失败计数原子化：`UPDATE sc_users SET login_failed_count = login_failed_count + 1 WHERE id = ?`，成功后清零；锁定用 `locked_until` 时间戳判断
- 锁定解除后**计数归零重新计**；连续锁定不延长窗口（简单可预期，避免放大 DoS）
- IP 限流维度使用 Nginx 层直连 IP（`$remote_addr`）+ `X-Forwarded-For` 取首个可信代理值（部署文档 §5 配置）

### 4.2 短信防轰炸（T9）

- 同一 `(country_code, phone)`：60 秒/次 + 10 次/日；同 IP 30 次/小时
- 发送幂等键 `X-Idempotency-Key`：同一请求窗口内重复调用返回首次结果
- 可选增强（生产建议开启）：单号单日失败 5 次触发该号当日禁发；IP 异常模式（多号高频）进风控名单
- 演示开关（规范 §1.10）：`SMS_MOCK=true` 时响应回显验证码，仅限 dev/test；生产 `SMS_MOCK=false` 或未开启对应通道时该能力 403

### 4.3 2FA 防爆破

- 失败 5 次 / 15 分钟并入账号失败计数（与密码同阈值，锁 423）
- TOTP 校验 ±1 时间步 + 同 time_step 防重放 + 恢复码一次性

## 5. 业务安全规则

### 5.1 防枚举（T1）

| 场景 | 规则 |
|---|---|
| 登录 | 账号不存在/密码错误/禁用/锁定 → 统一 10101 文案（423 锁定例外）；时序抹平（假哈希） |
| 注册 | 占用提示 409（16101）——注册必须明示占用，此为设计取舍（注册枚举不可完全避免），配合注册限流 + 演示开关图形验证码 |
| 忘记密码 | 账号不存在也返回成功（2.8 统一响应） |
| 发码 | 登录/注册二合一不区分；重置密码场景不报「账号不存在」 |

### 5.2 设备与异地判定（D5）

- 判定源：本地离线 GeoIP 库（登录热路径无远程调用，避免第三方故障拖垮登录）
- 基线：该账号**最近 30 天 / 最近 50 条成功登录**的城市分布；**省市级粒度**（同省不同市不算异地）
- 规则：
  1. 当前城市 ∈ 基线 → 正常
  2. 当前城市 ∉ 基线 → 标记 `is_unusual=1` → 异步发告警邮件（D9，仅邮件）
  3. 新城市成功登录累计 2 次 → 该城市计入基线（自动学习，防误报疲劳）
- **降噪**：信任设备（`is_trusted=1`）或最近 24 小时同城市已有成功登录 → 不重复告警；同一城市不同设备不重复告警
- 判定结果**随 sc_login_logs 首次写入落库**（不做事后 UPDATE，符合只追加）
- 首次登录（无基线）不告警，但会触发 2FA 提示（若已启用）

### 5.3 开放重定向防护（T7）

- OAuth `redirect_uri` 白名单：仅允许 `https://<前端域名>` 精确前缀匹配（配置项 `OAUTH_REDIRECT_WHITELIST`）
- 回调失败时仍 302 回白名单内的地址，杜绝拼接任意 URL

### 5.4 OAuth 回调完整性（T8）

- state：`random_bytes(32)` + 哈希存储 + 一次性消费（条件更新 `consumed_at`）+ TTL 5 分钟
- GitHub 用 OAuth App（code + client_secret）；Google 用 OAuth2（**PKCE S256**，code_verifier 经 AES-256-GCM 加密存于 sc_oauth_states（03 §3.6），随 state 一次性作废；客户端 secret 不必暴露在服务端调用链）
- code 换 token 失败 / 拉取用户失败 → 不建号、不绑定，返回 11102

### 5.5 KYC 防绕过（T11）

- 等级状态机单调递增：L0→L1→L2→L3，接口内校验当前等级（14101）
- 回调验签：第三方签名校验失败 14104，回调原文留痕（`callback_raw`）供审计追查
- 回调幂等：`(provider, provider_request_id)` 唯一约束，重复回调不改变状态（03 表设计 §sc_kyc_records）
- 三要素手机号须与本人绑定手机号一致（L1/L2 双重交叉校验）
- 同一身份证重复提交按日限次（3 次/日），防撞库式批量提交

## 6. Web 基础防护

### 6.1 响应安全头（Nginx / 应用中间件）

| 头 | 值（生产） |
|---|---|
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'`（按前端实际资源收敛） |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `X-Permitted-Cross-Domain-Policies` | `none` |

### 6.2 XSS 治理（T6）

- 所有 Cookie HttpOnly；前端不将敏感信息存 localStorage/sessionStorage
- Vue 默认转义插值，禁止 `v-html` 渲染用户内容；Element Plus 组件按默认安全配置使用
- CSP 收紧 `script-src 'self'`（不引入 CDN 脚本依赖）

## 7. 审计与合规

### 7.1 审计只追加双保障（规范 §1.7 强制）

| 层 | 保障 |
|---|---|
| 应用层 | sc_audit_logs / sc_login_logs 的 Model 层**禁 UPDATE/DELETE**（框架级拦截，调用即抛异常），仅允许 INSERT + SELECT |
| DB 层 | 创建**专用只写账号**（仅 INSERT + SELECT 权限），应用连接池使用该账号 → 即使应用被攻破也无法篡改历史 |
| 运维层 | 归档/清理走 DBA 专用通道（保留期到期迁移到冷存储，不物理删除近期数据） |

审计事件清单（action 常量，03 表设计）：`auth.login_success` / `auth.login_failed` / `auth.lockout` / `auth.logout` / `auth.logout_all` / `auth.password_changed` / `auth.password_reset` / `auth.2fa_enabled` / `auth.2fa_disabled` / `auth.recovery_code_used` / `refresh.reuse_detected` / `device.kick` / `device.trust_changed` / `oauth.bind` / `oauth.unbind` / `kyc.submitted` / `kyc.result_received` / `kyc.callback_received`

每条含：actor（user_id）/ target / ip / ua / request_id / detail_json（脱敏后上下文）→ 全链路可回溯（可观测性 §01-08）。

### 7.2 敏感数据处理（T10）

- **存储口径**（用户已确认）：敏感个人信息（证件号/银行卡号/手机号）**明文落库 + 接口脱敏**（规范 §2.4）
- 接口层为唯一脱敏源：手机号 `138****1234`、邮箱 `a***@domain`、证件号 `1101**********1234`、姓名 `张*`（02 API §1.7）
- 日志脱敏：应用日志与 access_log **不输出**验证码、密码、完整证件号、Cookie 原文；误输出由日志过滤器统一打码
- sc_kyc_records 留存完整请求/响应/回调原文（TEXT 列）供合规审计，查询权限收敛到管理员
- 合规删除：用户注销时仅逻辑删除（`is_deleted=1`）；审计与实名记录**按法规保留期留存**，不随注销删除（写入合规条款说明）

### 7.3 KYC 合规要点

- 第三方校验需签署条款（本系统仅负责对接，不存储第三方 SDK 采集的活体视频等原始生物特征——仅在 L3 流程中由 SDK 直接传输给第三方）
- 实名数据访问最小化：仅 `sc_kyc_records` 相关服务可读，日志与告警不含证件全文

## 8. 密钥与配置管理

### 8.1 密钥清单（全部仅存在于环境变量 / K8s Secret，禁止入库与提交）

| 密钥 | 用途 | 生成方式 | 轮换周期 |
|---|---|---|---|
| `APP_KEY` | 框架加密默认密钥 | `php bin/hyperf.php gen:key` | 发布事故时 |
| `JWT_SECRET` | Access 签名（HMAC-SHA256） | `random_bytes(64)` hex | 季度/泄露时（旧密钥宽限 2 倍 Access 时长） |
| `JWT_TICKET_SECRET` | totp_ticket / 一次性票据签名 | 同上 | 与 JWT_SECRET 同步 |
| `TOTP_ENCRYPTION_KEY` | TOTP secret 密文 AES-256-GCM | `random_bytes(32)` base64 | 年度（解密→新密文重写，下线离线批处理脚本） |
| `OAUTH_GITHUB_*` / `OAUTH_GOOGLE_*` | 第三方 App 凭据 | 各平台生成 | 按平台策略 |
| `KYC_PROVIDER_*` | 实名/活体服务密钥 | 厂商生成 | 厂商策略 |
| `SMTP_*` | 邮件通道 | 邮箱服务商 | 按服务商策略 |
| `CAPTCHA_SECRET`（启用时） | 图形验证码签名 | `random_bytes(32)` | 年度 |

### 8.2 配置分层（规范 §1.10）

- 分层：`config/*.php`（结构 + 默认值）← `.env`（环境差异）← 部署覆盖（K8s Secret/ConfigMap 挂载，见 05 部署）
- `.env.example` 入库，`.env` 不入库（`.gitignore`）
- **调试开关运行时门禁**：`SMS_MOCK` / `CAPTCHA_ENABLED` / 开发者工具类开关，生产环境开启一律 403 + 审计告警
- 生产检测脚本（05 部署 §3.4 门禁）：自动扫描 `.env` 中 `SMS_MOCK=true` / 空密钥 / 默认口令，阻断启动

### 8.3 密码算法升级路径

- bcrypt cost 从 12 起步；升级 argon2id 时：登录成功检测 `password_hash` 前缀，非新算法 → 顺手重哈希（渐进迁移，无停机）
