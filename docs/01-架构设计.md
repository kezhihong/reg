> 生产级登录注册系统 · 架构设计与关键决策

> 对应规范条款：§1.3 分层架构、§1.7 安全编码、§1.8 并发与事务、§1.9 性能、§1.10 配置与环境。

## 1. 系统概述

### 1.1 业务目标

提供一套生产级、可上线的账号体系：多方式注册登录、会话与设备管理、KYC 实名认证、登录安全防护（防暴力破解、异地登录告警）、全链路审计。本系统是独立的账号服务（Auth Service），可被业务方作为用户体系的底座。

**范围边界**：本期不含支付、商城、IM 等业务功能；不含管理后台（sc_users 表预留 `is_admin` 标记，管理端后续单独立项）。

### 1.2 功能清单

| 模块 | 能力 |
|---|---|
| 认证 | 账号+密码、手机号+短信验证码（登录注册二合一）、邮箱+密码、GitHub OAuth2、Google OAuth2 |
| 2FA | Google Authenticator（TOTP）+ 恢复码 |
| 会话 | JWT 双 token（Access 短时效 + Refresh 轮换可吊销）、全局吊销（token_version） |
| 设备 | 设备列表、踢设备、信任设备 |
| 实名 | KYC L0→L3（L1 手机号 / L2 证件三要素 / L3 人脸活体） |
| 安全 | 分层限流、账号锁定（423）、防用户枚举、CSRF 防护、OAuth state+PKCE |
| 日志 | 登录日志、审计日志（DB 只追加）、异地登录告警（邮件） |
| 运维 | Docker Compose 一键启动、stdout JSON 结构化日志（与 K8s 同构）、Promtail/Loki/Grafana |

### 1.3 规模假设（决定主键选型与架构形态）

- 用户量：10 万 ~ 500 万量级
- 登录 QPS：单机几十 ~ 数百；峰值横向扩展至多实例
- 数据量预估：sc_login_logs / sc_audit_logs / sc_refresh_tokens 为高增长表（日增可达十万级），主键用 `BIGINT UNSIGNED`；sc_users / sc_user_devices 等低增长表用 `INT UNSIGNED`（选型依据见 `03-数据库设计.md` §3）
- 部署形态：开发环境 Docker Compose 单机；生产逐步演进到 K8s（多实例）——架构上所有有状态依赖（会话校验不依赖内存、限流计数、队列）均落在 MySQL / Redis，保证多实例安全

### 2.2 技术栈选型理由

| 组件 | 选型 | 理由 |
|---|---|---|
| 后端框架 | Hyperf (PHP ≥ 8.1 + Swoole) | 常驻内存协程模型，性能与并发优于传统 FPM；异步队列、定时任务、WebSocket 内置；符合规范 §1.1「使用框架能力，不重复造轮子」 |
| 前端 | Vue 3 + Element Plus + Vite | 组合式 API + TS 生态成熟；Element Plus 组件库覆盖表单/表格/弹窗等全部页面诉求 |
| 数据库 | MySQL 8（InnoDB，utf8mb4_0900_ai_ci） | 唯一事实源；规范 §2 全章约束 |
| 缓存/队列 | Redis（可降级） | 限流计数、async-queue 持久化；无 Redis 时降级到 DB 表（见 D3/§6） |
| 部署 | Docker Compose → K8s | 本地一键启动；生产 K8s 化时架构不变（见 §9） |

### 2.3 两种部署形态的架构一致性原则

- **Compose 与 K8s 同构**：同一镜像、同一环境变量命名（前缀 `APP_`/`DB_`/`REDIS_`）、同一日志输出格式（stdout JSON）。K8s 迁移只改部署描述，不改代码。
- **无状态应用**：Hyperf 实例不保存任何会话/计数于进程内存（Swoole 协程内存只做进程级缓存，如 GeoIP 解析缓存，允许短暂不一致）。
- **有状态依赖显式化**：会话吊销（DB）、限流（Redis/DB）、队列（Redis/DB）均有明确的存储位置。

## 3. 分层架构

### 3.1 三层职责（规范 §1.3 强制）

| 层 | 职责 | 禁止 |
|---|---|---|
| Controller | 参数接收、格式校验、调用 Service、统一响应 | 业务逻辑、SQL、循环、复杂条件分支 |
| Service | 业务规则、流程编排、事务边界、审计事件 | SQL 细节、请求/响应对象污染 |
| Model | 表映射、关系、查询作用域、类型转换 | 业务规则 |

依赖方向单向：`Controller → Service → Model`，跨层禁止。同类实体聚合在同一 Service（如 `AuthService` 统一处理密码登录/短信登录/OAuth 回调的公共会话与设备逻辑，禁止散落多处改同一表）。

### 3.2 模块划分

| 模块 | Service 命名 | 核心职责 |
|---|---|---|
| 认证 | `AuthService` | 登录/注册/登出/刷新/改密，会话与设备编排 |
| 短信验证码 | `VerificationCodeService` | 发码（频控/幂等）、校验（哈希/次数/一次性） |
| OAuth | `OAuthService` | 第三方授权 state 生命周期、回调、绑定/解绑 |
| 2FA | `TotpService` | TOTP secret 加密管理、验证、恢复码 |
| 设备 | `DeviceService` | 设备指纹、列表、踢设备、信任标记 |
| KYC | `KycService` | 等级状态机、三要素/活体编排、回调幂等、人工复核 |
| 日志 | `AuditService` | 登录日志同步写、审计事件入队、批量落库 |
| 通知 | `NotificationService` | 邮件/短信发送队列、重试、通知记录 |
| 用户 | `UserService` | 资料查询与修改、手机号/邮箱绑定 |

### 3.3 公共组件

- **统一响应**：`{code, message, data}`（见 `02-API文档.md` §1）；业务异常统一继承 `BusinessException`（携带错误码 + 用户可读消息），禁止裸 `\Exception`（规范 §1.6）。
- **统一异常处理**：全局异常处理器兜底；5xx 响应禁止返回堆栈/SQL/框架内部信息，异常详情只进服务端日志；未匹配路由返回 JSON 404。
- **中间件链**（顺序）：
  1. `RequestIdMiddleware`（生成/透传 request_id，贯穿日志与审计）
  2. `RateLimitMiddleware`（IP 维度限流）
  3. `CorsMiddleware`（SPA 同源部署时仅允许同源，预留跨域配置项）
  4. `CsrfMiddleware`（登录态写操作校验双提交 token）
  5. `AuthMiddleware`（校验 Access Token，注入当前用户与设备上下文）
- **请求上下文**：协程上下文持有 `request_id / user / device / ip / ua`，供日志与审计统一取用。
- **事件与异步**：领域事件（`LoginSucceeded`、`AuditLogged`、`KycResultReceived` 等）→ async-queue 消费（见 §6）。

## 4. 认证子系统设计

### 4.1 登录主流程时序（含 2FA）

```
用户 → POST /auth/login（账号/邮箱+密码）
  ├─ RateLimitMiddleware: IP 限流 20 次/分钟 → 429
  ├─ Controller: 取参 + 校验格式（trim + 类型强转）
  └─ AuthService.login():
      ├─ 查询用户（唯一索引）→ 不存在 → 统一文案"账号或密码错误"（防枚举）
      ├─ 校验密码（password_verify, bcrypt）→ 失败 → 原子计数 +1
      │    └─ 达 10 次 → 锁定 15 分钟（423）+ 审计
      ├─ 校验锁定状态 → 锁定 → 423
      ├─ 校验 status / token_version
      ├─ [totp_enabled] → 返回"需二次验证"（临时会话票据，5 分钟）→
      │    POST /2fa/login/verify → 通过后继续
      ├─ 设备归并：读 device_key Cookie → 存在则更新设备行，否则新建
      ├─ 异地判定：GeoIP 归属地 vs 常用基线（D5）→ is_unusual 标记
      ├─ 发令牌：Access(15min) + Refresh(30d) → httpOnly Cookie
      ├─ sc_login_logs 同步写（与失败计数同事务）
      └─ 发布 LoginSucceeded 事件（unusual=1 → 异步告警邮件）
```

### 4.2 JWT 双 Token 机制（D1）

- **Access Token**：时效 **15 分钟**（配置可调 10–30 分钟），无状态 JWT（HS256，密钥来自环境变量）。Payload：`uid`、`ver`（sc_users.token_version 快照）、`did`（device_id）、`iat`、`exp`。**不做黑名单**——即时吊销依赖短时效 + token_version。
- **Refresh Token**：时效 **30 天**（固定，轮换时重新起算）。`random_bytes(32)` 生成，**不存明文**：仅存 `sha256(salt + token)`（每 token 独立随机 salt，16 字节 hex），比较用 `hash_equals`（规范 §1.7 一次性凭证条款）。
- **传输**：双 token 均存 httpOnly Cookie（规范强制，禁止响应体返回明文令牌）：
  - Access Cookie：`SameSite=Strict`、`Secure`（生产）、`Path=/api`
  - Refresh Cookie：`SameSite=Strict`、`Secure`（生产）、`Path=/api/v1/auth/refresh`（缩小暴露面）
- **轮换**：每次 refresh 签发新 token，并原子作废旧 token（条件更新 `rotated_at`）；Refresh Token 行存独立表保留轮换历史（供重用检测与审计）。
- **重用检测**：收到一个已轮换/已吊销的 refresh token → 判定泄露 → **吊销该设备全部会话**（该 device 全部 refresh 行 + 设备行）+ 审计 `refresh.reuse_detected`。
- **并发刷新处理**：同一设备多标签页并发 refresh 为合法场景。方案：刷新事务内 `SELECT ... FOR UPDATE` 设备行（短事务，仅 2–3 条 UPDATE，符合规范 §1.8 悲观锁条款）串行化；若携带 token 已被轮换且请求来源（设备 Cookie + IP）与轮换者一致 → 视为并发重试放行；不一致 → 判重用。Redis 锁为可选加速项，不依赖。
- **全局吊销（token_version）**：`sc_users.token_version` 自增后所有已签发 Access 立即失效（JWT 校验比对 `ver`）；Refresh 刷新时发现版本落后同样拒绝。触发点：修改密码、关闭/重置 2FA、管理员禁用账号、强制全部下线。
- **校验失败语义**：expired / revoked / version 差异只在服务端日志区分，响应统一 401 + 通用文案；任何响应体、日志、异常消息不得出现明文令牌。

### 4.3 登出与踢设备

- 登出当前设备：吊销该设备全部 refresh 行 + 清 Cookie。
- 踢设备（D2）：`DELETE /devices/{id}` → 条件更新设备行 `revoked_at`（`WHERE id=? AND revoked_at=0` 防重复踢）→ 该设备全部 refresh 行置 revoked（reason=踢设备）→ 审计。被踢设备下次 refresh 得 401 → 前端清 Cookie 引导重新登录。当前设备被踢等同登出。

## 5. 第三方集成设计

> 原则：所有第三方调用**异步化**（队列任务），绝不进入主流程事务（规范 §1.8「事务内禁止远程调用」）；第三方接口全部经抽象接口，Mock/真实实现由配置路由，生产无第三方凭证时系统可用（门禁语义见 `04-安全设计.md`）。

| 抽象接口 | 实现 | 用途 |
|---|---|---|
| `SmsProviderInterface` | `MockSmsProvider`（dev/test：验证码回显日志，仅门禁开启可用）/ `AliyunSmsProvider`、`TencentSmsProvider` | 短信发送 |
| `EmailProviderInterface` | `MockEmailProvider`（输出日志）/ `SmtpEmailProvider` | 异地告警、重置密码邮件 |
| `OAuthProviderInterface` | `GithubOAuthProvider`、`GoogleOAuthProvider` | 授权码换取、用户信息拉取 |
| `KycProviderInterface` | `MockKycProvider`（dev/test 固定通过）/ `RealKycProvider` | L2 三要素校验、L3 活体 |
| `GeoIpInterface` | `Ip2RegionProvider`（本地离线库，进程内缓存） | IP 归属地解析 |
| `CaptchaProviderInterface` | 默认无实现（关闭）；生产建议接入 | 图形验证码（预留） |

### 5.1 OAuth2 设计要点

- 授权码模式 **Authorization Code + PKCE (S256)**；`state = random_bytes(32)`，**只存哈希**（sha256+salt，`hash_equals` 比较），一次性消费（条件更新 `consumed_at`），TTL 5 分钟，state 绑定 provider + redirect_uri；登录态绑定场景额外绑定 user_id（防 CSRF 式绑定攻击）。
- 回调验签（有签名场景）：`verifyCallbackSignature` 由 Provider 实现。
- 首次第三方登录自动建号（`sc_user_identities` 落 provider + provider_user_id）；OAuth 建号的用户 `password_hash=''`（未设密码），首次登录引导设置密码或绑定手机号。
- 第三方 access_token / refresh_token 使用 **AES-256-GCM 加密存储**（独立随机 nonce），密钥来自环境变量，不落明文（规范 §1.7）。

### 5.2 KYC 第三方（详见 D6 与 `02-API文档.md` §6）

- L2 三要素（姓名 + 证件号 + 手机号）异步校验，回调 + 轮询双通道；`provider_request_id` 唯一索引兜底回调幂等。
- L3 人脸活体：前端 SDK 采集 → 服务端发起异步校验 → 回调/轮询回写。
- 第三方原始请求/响应全部留痕（sc_kyc_records TEXT 列，只追加）。

### 5.3 GeoIP

- 本地离线库（ip2region 类），进程内缓存（TTL 数小时）；登录热路径**零远程调用**；归属地解析在 Controller 前置完成（缓存命中），结果随 sc_login_logs 落库（不事后 UPDATE）。

## 6. 异步与队列设计

- **队列选型**：Hyperf async-queue + Redis 持久化（进程崩溃不丢）；无 Redis 时降级 DB 队列表（同 `sc_rate_limits` 的降级思路，生产推荐 Redis）。
- **任务清单**：

| 任务 | 触发 | 说明 |
|---|---|---|
| `SendEmailTask` | LoginSucceeded(unusual=1) / 重置密码 / 2FA 安全通知 | 异地告警邮件；失败重试 3 次指数退避 → 死信 + 告警 |
| `SendSmsTask` | 验证码发送 | 频控在发送前已校验，任务内仅投递 |
| `AuditBatchWriteTask` | 审计事件入队 | **批量插入**（数百条/批，规范 §1.9）；消费端只 INSERT |
| `KycVerifyTask` | L2/L3 提交 | 调第三方 + 回写 sc_kyc_records + 事件 |

- **重试与死信**：所有任务幂等（业务唯一键：如 kyc provider_request_id、notification 记录 id、audit batch id）；重试指数退避（1m/5m/30m，最多 3 次）→ 死信队列 → 运维告警。
- **与主事务解耦**：事件在事务提交后发布（`afterCommit`），发送失败绝不影响登录结果。

## 7. 前端架构（Vue 3 + Element Plus）

### 7.1 目录结构

```
frontend/
├── src/
│   ├── api/            # axios 封装 + 按模块接口（auth/oauth/tfa/device/kyc/log）
│   ├── stores/         # Pinia：user / devices / notifications
│   ├── router/         # 路由 + 守卫（登录态、2FA 中间步骤、KYC 等级门禁）
│   ├── views/          # 登录 / 注册 / 2FA 验证 / 设备管理 / KYC / 日志 / 通知
│   ├── components/     # 通用组件（OAuth 按钮、验证码输入、脱敏展示）
│   ├── utils/          # request_id 透传、脱敏工具、错误码映射
│   └── constants/      # 状态常量（与后端常量一一对应）
```

### 7.2 关键机制

- **Cookie 凭据模式**：axios `withCredentials: true`（同源部署时同域 Cookie 自动携带）；401 静默刷新：响应拦截器捕获 401 → 调 `/auth/refresh` 重放原请求（单飞：并发 401 合并为一次刷新）；刷新失败 → 清状态跳登录页。
- **路由守卫**：登录态校验（`/auth/check` 或本地 token 状态 + 兜底）；2FA 中间步骤页（临时票据）；KYC 等级门禁（页面按 kyc_level 展示/解锁）。
- **状态管理**：Pinia 持久化 user 基本信息（脱敏后）；设备列表页支持「踢设备」「信任设备」交互与二次确认。
- **脱敏展示**：手机号/邮箱/证件号统一走脱敏组件（与后端返回的脱敏值一致，前后端双保险）。

## 8. 可观测性

### 8.1 日志规范（与 K8s 同构）

- 一律 **stdout** + **JSON 结构化**（Monolog StreamHandler → `php://stdout`），字段固定：`ts / level / logger / request_id / user_id / device_id / action / msg / context`。
- 本地 Docker Compose 与 K8s 同一输出格式，迁移零改动；采集链 Promtail → Loki → Grafana（配置见 `05-部署运维.md` §4）。
- 日志禁止出现：密码、令牌、验证码、证件号明文（规范 §1.6/§1.7）。

### 8.2 指标项

| 指标 | 来源 | 关注点 |
|---|---|---|
| 登录成功/失败数（按方式） | sc_audit_logs | 环比突变 = 攻击/故障信号 |
| 限流命中数（按维度） | sc_rate_limits / 日志 | 攻击面探测 |
| 2FA 失败率 | sc_audit_logs | 误触 / 攻击 |
| 锁定触发次数 | sc_audit_logs | 暴力破解 |
| 第三方接口失败率 | sc_kyc_records / sc_notifications | 依赖健康 |
| refresh 重用检测次数 | sc_audit_logs | 令牌泄露 |

## 9. 演进路线

## 10. 关键设计决策汇总（D1–D9）

> 本节为全文决策基线：`03-数据库设计.md`（表结构）、`02-API文档.md`（接口）、`04-安全设计.md`（策略）只引用本节，不推翻。

### D1. JWT 双 Token（详见 §4.2）

Access 15 分钟无状态（payload: uid/ver/did）；Refresh `random_bytes(32)` 只存 `sha256(salt+token)`，独立表留轮换历史；双 Cookie（Access Path=/api，Refresh Path=/api/v1/auth/refresh，SameSite=Strict，生产 Secure）；轮换事务 `FOR UPDATE` 设备行防并发；重用检测 → 吊销设备全部会话 + 审计；`sc_users.token_version` 全局吊销（改密/关 2FA/禁号/全部下线触发）；明文令牌禁止出现在响应与日志。

### D2. 设备管理（详见 §4.3）

设备指纹由**服务端生成**（32 字节 `random_bytes` hex 的 `device_key`，httpOnly Cookie 有效期 1 年），不信任客户端指纹；首次登录建设备，后续登录归并更新；踢设备 = 条件更新 `revoked_at`（防重复踢）+ 吊销设备全部 refresh + 审计；`is_trusted` 信任标记（异地判定豁免，见 D5）。

### D3. 防暴力破解

分层限流（429）：IP 20 次/分钟、账号 10 次失败/15 分钟、短信 60 秒/次 + 10 次/日、IP 30 次/小时（短信）；账号锁定 10 次失败锁 15 分钟（423），失败计数与锁定用**原子 UPDATE**；锁定触发/解除写审计；登录失败统一文案防枚举；注册/重置对不存在凭证返回与存在一致的响应；图形验证码 `CaptchaProviderInterface` 预留、默认关闭（生产建议失败 ≥3 次后启用，演示环境以 sms-mock 回显 + 限流锁定兜底）；OAuth state 只存哈希 + 一次性 + PKCE(S256)。

### D4. 短信验证码

6 位数字 `random_int(100000, 999999)` 服务端生成；**只存 `sha256(salt+code)`**，验证 `hash_equals`；频控 60 秒/次 + 10 次/日；TTL 5 分钟、验证次数上限 5 次（超限作废）、一次性（条件更新 `consumed_at`）；登录注册二合一（发码接口不区分，验证后按手机号查号，无号自动注册）；发送带幂等键（scene+phone 窗口去重）；mock 回显仅 dev/test 门禁开启可用，生产关闭返回 403。

### D5. 异地登录判定与告警（仅邮件）

数据源本地离线 GeoIP 库 + 进程内缓存，登录热路径无远程调用；基线 = 最近 30 天 / 50 条成功登录的城市集合；本次城市 ∉ 基线 且 设备非信任 → `is_unusual=1`；**同省放宽**（城市不同但同省不算异地）；新城市 30 天内出现 ≥2 次自动入基线；信任设备豁免；内部/演示账号白名单（配置项）；判定在登录事务内完成、随 sc_login_logs 落库（只追加不 UPDATE）；告警邮件异步发送（D9），含时间/城市/设备/指引，不含任何令牌。

### D6. KYC 实名认证（L0→L3）

等级单调递增（L0→L1→L2→L3，不可降级）；每次提交生成 sc_kyc_records 记录，状态机 submitting → reviewing → approved / rejected / expired；L1 复用短信验证码通道（通过即 `is_phone_verified=1`、kyc_level≥1）；L2 三要素（姓名+证件号+手机号）异步队列 + 第三方 API，回调验签 + 轮询双通道，`provider_request_id` 唯一索引兜底幂等，配置开启人工复核（reviewed_by/reviewed_at）；L3 活体（前端 SDK 采集，异步回调）；`KycProviderInterface`（Mock 固定通过 / 真实）；请求体/第三方响应/回调原文全部留痕 TEXT；证件号**明文落库、接口只返回脱敏值**；证件照片类文件走对象存储 + 访问控制 + 到期清理任务（规范 §2.7）。

### D7. 2FA（TOTP）

32 字节 `random_bytes` secret，Base32 编码；**AES-256-GCM 加密存储**（每用户独立随机 nonce，密钥环境变量）——TOTP 验证必须能计算 HMAC，单向哈希不可行，加密是行业标准做法（规范 §1.7「声称必须真实实现」：文档承诺加密就必然加密）；`enable/start` 返回 otpauth URI，用户 6 位码验证通过**才持久化**；30 秒步长 ±1 时间步容差（服务器时钟权威，生产需 NTP）；同一时间步防重放；**10 个恢复码**逐码 `random_bytes(8)` + 独立盐哈希 + 一次性消费，2FA 关闭全部作废；恢复码用尽走客服人工流程（审计 + 风控标记 + 多要素验证）；2FA 验证失败计入账号失败计数（与密码同阈值）；登录集成：首步成功后返回「需二次验证」临时票据（5 分钟），验证通过才发令牌。

### D8. 登录日志与审计日志

sc_login_logs：登录 Service **主事务内同步写**（与失败计数/锁定同事务，保证一致），只追加；字段含 user_id（失败未知为 0）、login_type、is_success、fail_reason、IP+归属地、UA、device_id、is_unusual、request_id。sc_audit_logs：覆盖敏感操作（注册、登录成败、改密、2FA 变更、踢设备、KYC 状态变更、锁定触发、重用检测），异步队列**批量插入**（数百条/批）；**只追加双重保障**：应用层消费端禁止 UPDATE/DELETE + DB 应用账号仅授审计表 INSERT/SELECT（规范 §2.7 最小权限）；按月归档，保留期配置化，归档任务落地实现（规范 §2.7「不允许只写注释不实现」）。

### D9. 异地告警「仅邮件」异步实现

登录事务提交后发布 `LoginSucceeded` 事件（user_id/ip/归属地/device_id/is_unusual）→ async-queue 消费者：unusual=1 构造邮件 → `EmailProviderInterface` 投递（SMTP，mock 输出日志）→ sc_notifications 表记录（pending/sent/failed + retry_count + next_retry_at，失败重试 3 次指数退避 → 死信告警）；发送失败**绝不影响登录结果**（事务外、队列解耦）；sc_notifications 同时承载重置密码邮件等场景（channel/scene 可扩展）。
